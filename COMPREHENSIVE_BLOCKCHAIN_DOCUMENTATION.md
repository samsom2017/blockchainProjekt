### 2.3 Hash Function (Cryptographic)

A hash is like a unique fingerprint for data.

**Example**:
```
Input Data: "Patient Alice, Age 30"
Hash Output: 9ed0a8d307d634a31a3d9b5a4a262443b6ac82d5244a3c44e19f45695bb87e16

Input Data: "Patient Alice, Age 31"  (changed 1 character)
Hash Output: f1745a3ae916ce81dd69d1c5062d9b8fcbe643f3b094fd91960f72e7727285fe
(completely different!)
```

**Important Property**: Even a tiny change in data produces a completely different hash.

### 2.4 Immutability (Can't Be Changed)

**Why Data Can't Be Tampered With**:

Imagine you try to change Block #2's data:
```
Original Block #2:
- Data: "Vitals: BP=120/80"
- Hash: f1745a3ae916ce81dd69d1c5062d9b8fcbe643...
- Previous: 9ed0a8d307d634a31a3d9b5a4a262443b6ac...

Hacker changes it to:
- Data: "Vitals: BP=130/85"
- Hash: f1745a3ae916ce81... (still old!)
- Previous: 9ed0a8d307d634a31... (still old!)

Problem: The hash doesn't match the new data!
Also, Block #3 now points to the wrong hash.
And Block #4 points to the wrong hash.
... entire chain breaks!
```

**Result**: Everyone immediately knows the blockchain was tampered with.

### 2.5 Chain Validation

The system checks:
1. Is each hash correct for its data?
2. Does each block's "previous hash" match the actual previous block's hash?
3. Are they linked in order?

**Our System Checks**:
```
validateChain() {
    expectedPrevHash = "0"  // Genesis (first block)
    
    For each block:
        If block.prevHash != expectedPrevHash:
            Return FALSE (chain is broken)
        expectedPrevHash = block.hash
    
    Return TRUE (chain is valid)
}
```

## SECTION 3: EVENT-DRIVEN ARCHITECTURE

### 3.1 What is Event-Driven Architecture?

**Definition**: A system design where components communicate through events rather than direct calls.

### 3.2 Traditional Architecture (Direct Calls)

```
Patient Registration System ? Blockchain ? Dashboard
         ?
   Direct function call
         ?
   Waits for response
         ?
   Continues...
```

**Problems**:
- Tight coupling
- If dashboard is slow, registration is slow
- Hard to scale

### 3.3 Event-Driven Architecture (Our System)

```
????????????????????????????????????????????
?         EVENT BUS / MESSAGE QUEUE        ?
?                                          ?
?  "Patient Registered"  ?  Blockchain    ?
?  "Vitals Updated"      ?  Dashboard     ?
?  "Test Completed"      ?  Notifications ?
????????????????????????????????????????????
         ?                       ?
         ?                       ?
    Producers               Consumers
```

### 3.4 Event Flow in EDSC

**Step 1: Event Generation**
```
User registers patient ? "PatientRegistered" event created
User updates vitals    ? "VitalsUpdated" event created
```

**Step 2: Event Storage**
```
Event saved to events list (shared by all components)
```

**Step 3: Event Processing**
```
Blockchain system reads event ? creates block
Dashboard reads event ? displays in real-time
Web API reads event ? sends to frontend
```

### 3.5 Benefits of Event-Driven

? **Loose Coupling**: Components don't know about each other
? **Scalability**: Can add new consumers without changing producers
? **Real-Time Updates**: Dashboard updates immediately
? **Auditability**: Every event is recorded
? **Flexibility**: Easy to add new features

#### 2. **EDSC.java** (Core Blockchain Logic)
```java
public class EDSC {
    List<BlockchainEvent> events;
    
    // Creates a new block from event data
    public void addEvent(String data) {
        BlockchainEvent newEvent = new BlockchainEvent(
            data,
            calculateHash(data),
            previousHash
        );
        events.add(newEvent);
    }
    
    // Verifies blockchain hasn't been tampered with
    public boolean validateChain() {
        String expectedPrevHash = "0";
        for (BlockchainEvent event : events) {
            if (!event.getPrevHash().equals(expectedPrevHash)) {
                return false; // Chain is broken!
            }
            expectedPrevHash = event.getHash();
        }
        return true; // Chain is valid!
    }
}
```

**Purpose**: The heart of the blockchain system

**What It Does**:
1. Receives events from hospitals
2. Creates blocks with cryptographic hashes
3. Links blocks together
4. Validates chain integrity
5. Detects tampering

### 7.3 Hash Calculation (Technical)

```
Input Data: "Patient Register P001: Alice at City Hospital"

Step 1: Convert to bytes
   P a t i e n t   R e g i s t e r ...
   80 97 116 105 101 110 116 ...

Step 2: Apply SHA-256 hashing algorithm
   (One-way mathematical function)
   
Step 3: Get hash output
   9ed0a8d307d634a31a3d9b5a4a262443b6ac82d5244a3c44e19f45695bb87e16
   
   Properties:
   - Always same for same input
   - Different for any change
   - Can't reverse (one-way)
   - Fixed length (256 bits)
```

## SECTION 11: TROUBLESHOOTING & FAQs

### 11.1 Common Questions

**Q: What if the chain becomes invalid?**
A: If someone tampers with a block, hashes won't match. System detects instantly and displays "Chain Status: BROKEN" in red.

**Q: Can I add events after startup?**
A: Yes! Use menu option 2 to register new patients. Each registration creates a new block automatically.

**Q: Why does the dashboard update every 2 seconds?**
A: Auto-refresh ensures real-time visibility of new events and system status.

**Q: Can I delete events?**
A: No - immutability is a feature, not a bug. All historical records are preserved.

**Q: What if a hospital goes offline?**
A: In production, replicas would be distributed. Here, all data is in shared memory.
